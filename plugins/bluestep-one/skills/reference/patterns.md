# Patterns

Prefix `P`. Patterns that hold for any BlueStep One component.

---

### P-14 — Read rights up front over `/gql`; on a release without them, try the write and fall back to read only on a refusal

Legacy shape: Manage hides or greys actions by the user's groups (though not on every page). BlueStep One shape: the host has no read of the viewer's level on a form or entry; `session.currentUser().isAdmin` is the only flag. So, on a release without the rights fields below, the screen shows its actions, and the first write that comes back refused (`host.isRefused(error)`, code `FORBIDDEN`) switches it to read only, with the server's own words. A network failure is told apart and offered again; a refusal is not retried (R-54).
Before release 26.10.26, `/gql` is no way round it: `user { parents }` is empty for a Super user and for a staff user alike (still so on 26.10.13.01), though the form's `permissions` list its Editor groups. Only `user { super }` (or the host's `isAdmin`) is known up front: a Super viewer can edit; everyone else gets the actions and the refusal path.
From release 26.10.26.01, `/gql` serves `FormRow.canEdit` / `canDelete`, cell `canEdit` and `RelateForm.createLevels(record) { canCreate creatableFields }`, so a component reads the viewer's rights with its rows and draws read only on load (P-76). The try-and-refuse path stays as the fallback (a failed rights read, a right that changes while the screen is open), and is the whole answer only on an org before 26.10.26. A probe write on load to learn the rights is no longer needed.
**How to tell.** 1. On a test org, from a component, read `host.session.currentUser()`: only `isAdmin`; nothing about the viewer's level on a form. 2. Over `/gql`, as a staff user with read rights only, read a row's `canEdit canDelete`, the cells' `canEdit` and `createLevels(record)` on its form: `false` where the viewer may not act (the row flag alone can read true for a user with field-level Editor on a few fields). 3. As a staff user without Edit, try a write on test data: `FORBIDDEN`, and the screen turns read only.
**Applies to:** any BlueStep One component

### P-32 — A canvas's div grid table, built as a real table whose rows are CSS grids

Legacy shape: Manage draws lists as `<table>`. Canvas shape: rows of `display:grid` divs with a fixed `grid-template-columns` (e.g. `minmax(0,1.3fr) 128px …`). BlueStep One shape: keep the table semantics and match the canvas exactly by setting `display:block` on `table`, `thead` and `tbody`, `display:grid` with the canvas template on each `tr`, and explicit `role="table|rowgroup|row|columnheader|cell"` (the display change drops the implicit roles). Below a minimum width the card scrolls sideways inside itself rather than squeezing a column to nothing. A shared row component (a hover tint, a click to open) keeps working. The same result can also be drawn with no `table` element at all: a `div` with `role=table` holding `div` rows with `role=row`, each row a CSS grid. Either way the roles must be set by hand. When not to use: a list the host's own list engine can draw.
**How to tell.** 1. On a test org, open a component screen that draws such a table and inspect it: `table`, `thead` and `tbody` are `display: block`, each `tr` a grid with the canvas's `grid-template-columns`, and each element carries its `role` (`thead` has `role=rowgroup`). 2. Narrow the window below the minimum width: the card scrolls sideways; a screen reader still reads a table.
**Applies to:** any BlueStep One component

### P-33 — Four kit idioms the canvas needs: tabs in a toolbar row, a link-looking real link, a wider dialog, headings under the page title

(1) Tabs sharing a row with a filter: put the whole row inside `B6pTabs` (the tabs list needs its context) and set `marginTop: 0` on `B6pTabsContent`, which the kit gives `mt-2`. (2) A link drawn as the canvas's link button: `B6pButton variant="link" asChild` around a real `<a href>`, so middle-click and copy-link work; the kit's Slot merges `style` and `onClick`. (3) A wider dialog: `className="sm:max-w-3xl"` on `B6pDialogContent`, the kit's own advice, which keeps the mobile gutter and the height cap. (4) `PageContentTitle` draws an `<h1>` (the host's record header is an `<h2>` above it), so a screen's section headings under it are `<h2>`, not `<h3>`.
**How to tell.** 1. On a test org, open a component screen built this way: the tabs and the filter share one row inside `B6pTabs`, and the content has `margin-top: 0`. 2. Middle-click the link button: it opens in a new tab (a real `<a href>`). 3. Open the wide dialog: it carries `sm:max-w-3xl`. 4. The screen's section headings are `<h2>` under the page's `<h1>`.
**Applies to:** any BlueStep One component

### P-34 — A click that starts a slow host navigation marks its own control until the next screen arrives

Legacy shape: Manage loads a new page, and the browser's own loading shows the click took. BlueStep One shape: `formEntries.openEntry` hands the route to the host, which runs its reads before it mounts the next screen. How long the screen stays nearly empty has changed from build to build: one host fix made the skeleton show 9 to 87 ms after the address moved; on a later build the skeleton (`[class*=skeleton]` or `aria-busy`) showed only at 0.75 to 1.3 s and the entry at 1.5 to 2 s; on another, the host's reads after `openEntry` ran to 3.3 s. So measure it on the build in front of you.
When the gap is long, the component marks the control clicked, before calling the host: `aria-busy` and a progress cursor on the row, a small muted loader in space the text does not use (a negative margin into the row's padding, so nothing moves), the kit's leading icon inside a button, a polite "Opening <name>…" status for screen readers, every other click to open ignored, and a fallback that clears the mark after 15 s if the screen is still there. No overlay, no page-wide spinner. Drop the mark for host hops when the host shows its own skeleton at once. It still applies to a component's own work before it calls the host (a lookup that takes 0.5 to 2.5 s).
When the mark goes, keep its guard, unseen. Without it a double-click calls `openEntry` twice inside the host's 20 to 90 ms, the address is pushed twice, and *Back* first lands on the same entry. Drop a second click to open within 1 s, and count two clicks in one frame once (keep the flag in a ref). With no mark to draw, the host's skeleton came sooner too: 20 to 27 ms after the click instead of 72 to 88.
**How to tell.** 1. On a test org, open an entry from a component's list with the network panel open, and time the gap from the click to the host's skeleton and to the next screen. 2. Double-click a row: with the guard, the address is pushed once, and *Back* leaves the entry.
**Applies to:** any BlueStep One component

### P-35 — To see a component's error and read-only screens without another user, fail its reads and refuse its writes inside the page

Legacy shape: in Manage an error or a no-rights page needs a broken server or a user with fewer rights. BlueStep One shape: a component calls the global `fetch` for `/gql` at call time, in the host's own window, so a wrapper set from the console (after the app has loaded) reaches it across the host's hash navigation. `${CLAUDE_PLUGIN_ROOT}/tools/fetch-wrapper.js` is that wrapper; it reads the operation name from each POST body. For a failed load, answer the component's list read with the server's own INTERNAL shape, HTTP 500 and `{"errors":[{"message":"An unexpected server error occurred.","extensions":{"classification":"INTERNAL"}}]}` (`fw.fail("<read>")`), then move to the page so the component mounts and reads. For read only, answer **every** mutation with HTTP 200 and a `FORBIDDEN` error carrying the server's words, and never pass one on (`fw.refuse()`); then use any action on test data. Check the rules are still in place before each confirm, keep a log of what the wrapper stopped (`fw.log`), and put the original `fetch` back at the end (`fw.restore()`, or reload). The host's own writes go through `/gql` too (`RecordRecordView`, the recent-records list) and get stopped with the rest, which is harmless. The host keeps its writes in a browser queue, where a save can wait unsent and go out after a reload; check its corner badge shows nothing waiting afterwards. This shows the screen, not the server: walk the real refusal once with a real user who lacks the right. Use a test org or a sandbox, never a real org.
More states with nothing sent:
- The saving state and the after-save screens: a small wrapper of your own over `fetch` answers the create after a hold, with the server's shape (`{ "data": { "createFormRow": { "id": "<n>___<n>", "rowVersion": 2 } } }` for a success, the INTERNAL shape for a failure), and never calls the real `fetch` for a mutation. Leave `fw.refuse()` underneath as a second guard. That shows the spinners, a partial save (one saved, one "not saved") and the report. `fetch-wrapper.js` has no rule for this yet.
- Holding the read that comes before a write (`fw.delay("<read>", 9000)`) shows the marking and saving states. `fw.change` and `fw.refuse` on a filter's reads reach the filter's states. Answering the host's own `FormEntries` list empty (`fw.empty`) reaches an entry that does not open. A `matchMedia` stub that answers `(prefers-reduced-motion: reduce)` in the frame shows the still spinners. When an entry opens, the host's own `RecordRecordView` mutation is refused with the rest; that only skips a recent-views entry.
- A partial failure (a write that did not reach one entry) is drawn by letting a real write on test data go through and changing only the screen's read after it.
- A state no read of the page holds is made by changing a read's answer. An entry dated after the org's today is drawn by `fw.change("<day read>", …)` moving an unsigned row's date field (`<field id>`, `value.dayOfMonth` and `valueAsString`) one day on. The row on the server is unchanged, so a save from that card writes today's row: save only test data there, or nothing.
- A setting the org may not change is reached the same way: `fw.change("<settings read>", "data.<setting>.valueAsString", "false")`. A component that reads its settings once per load needs a switch of unit away and back (or another page and back) after the rule is set.
**How to tell.** 1. On a test org, after the app has loaded, paste the wrapper and answer the component's list read with HTTP 500 and the INTERNAL shape, then move to the page: the error screen shows. 2. Answer every mutation with HTTP 200 and a `FORBIDDEN` error, then use an action on test data: the read-only screen shows, and nothing reached the server. 3. Put the original `fetch` back (or reload).
**Applies to:** any BlueStep One component

### P-37 — Publish a custom component once per screen, name the commit in the request, and see that commit served before a live check

Legacy shape: a Manage edit is live on save, so every change is checked at once. BlueStep One shape: a push reaches nobody until a tenant admin presses *Rebuild draft* and *Publish* (3 to 19 minutes from commit to publish in one build), every publish breaks tabs left open, and the *Build* tab cannot show whether a push is waiting.
So: tasks that change only rules or data stop at the type-check and tests; a screen gets one publish when its tasks are all in, one live check of every artboard it draws, then one fix-up publish. Each publish request names the commit (`draft@<sha>`). After the publish, do a full reload (F5); then the network panel must show `/component/<name>/<sha>` before anything is checked. The served `/component/<name>/<sha>/remoteEntry.js` matches the component's `publishedSha`. The usual mistake: a live check run on the build published before the last push.
When not to use: a fix a reviewer is waiting on, alone; publish it at once.
**How to tell.** 1. Push a component's commit to `draft`, then build and publish it (`buildCustomComponent`, `publishCustomComponent` over `/gql` from a signed-in tab, `build/publish.md`). 2. Reload the page (F5) and, in the network panel, find `/component/<name>/<sha>`: only when the sha is the commit pushed is a live check made.
**Applies to:** any BlueStep One component

### P-38 — Give every `/gql` write its own `X-Request-Id`, and resend with the same id after a lost answer

Legacy shape: a Manage save posts once; a lost answer means the user looks and saves again by hand.
BlueStep One shape: the host's own writes over `/gql` carry an `X-Request-Id` header. The server keeps the first answer per session and id for 24 hours and replays it on a repeat, so a lost answer is recovered by sending again, not applied twice. The live SDL (26.10.06.00) says the same for every request: "X-Request-Id replays a repeat exactly, as for every /gql request". The server's duplicate check (since 26.09.15) keeps only 2xx answers, a refusal sent as HTTP 200 included, and does not compare the body.
A component that calls `/gql` itself sends no id unless it adds one, so a write resent after a timeout could land twice. So: mint one id per intended write (one entry's save), send it as `X-Request-Id` beside the CSRF header, and on a network failure or a lost answer resend the same body with the same id; a new attempt by the user gets a new id.
Keep the id by the exact body sent (`JSON.stringify({ query, variables })`): no answer at all (a network error, an abort) keeps it under that body, any answer ends it, so the same save sent again after a lost answer goes out under the old id and anything changed goes out under a new one. A bare HTTP 403 (a stale CSRF token, the server ran nothing) is retried once under the same id; the server keeps only 2xx answers, so nothing was stored for it. Tell a write from a read by the first keyword after whitespace, commas and `#` comment lines, so a comment cannot send a write out with no id.
The same id needs the same body, and a write that carries a version read just before it does not keep its body: after a lost answer whose write did land, the fresh read finds a newer version, so the resend is a new body, gets a new id and runs twice. Remember the version a write with no answer went out with (by entry, field and what it means, such as the day) and send that version again, so the body and the id hold; any answer ends the memory. A write whose result the entry itself shows (a filter that already holds what was asked) needs no memory: read first and send nothing.
Checked live on saves from a signed-in tab (the last check on 26.10.13.01, an `updateFormRow`): the same body with the same id a few seconds later comes back in about 210 ms as the first answer, with no new version in `history` and no second entry or signature. A changed value under a new id at the stale version is refused: `CONCURRENT_MODIFICATION` with `currentVersion`. The same body under a new id, when the entry already holds those values, answers success at the current version with no new version, since a no-op is not version-checked.
When not to use: a read; a write the server refuses (the refusal is the answer to replay).
**How to tell.** 1. On a test org, from a signed-in tab, send one `updateFormRow` on a test entry with an `X-Request-Id`, then the same body with the same id a few seconds later: the first answer comes back again, and `history` shows no new version. 2. Send a changed value with a new id and the old `expectedVersion`: `CONCURRENT_MODIFICATION`.
**Applies to:** any BlueStep One component

### P-43 — A hand-built clickable card takes the kit's focus ring by class: the host's stylesheet has those classes

Legacy shape: a Manage list row is a link and the browser draws its focus. BlueStep One shape: when a whole `B6pCard` is the control (`role="button"`, `tabIndex={0}`, Enter and Space call the same handler as a click), give it `className="ring-offset-background focus-visible:ring-ring focus-visible:ring-2 focus-visible:ring-offset-2 focus-visible:outline-none"`, the ring `B6pTabsTrigger` and `B6pButton` draw. The host's Tailwind build ships only the classes the kit uses, and the kit uses these, so they resolve. When not to use it: for any other variant the kit does not use (`motion-reduce:`, `motion-safe:`, a palette shade), which the build leaves out (G-157; the same holds for palette variables a canvas uses that the host's stylesheet does not ship); and where a kit button fits, use the button.
**How to tell.** 1. On a test org, open a component screen with such a card and press Tab onto it: the kit's ring draws (`focus-visible:ring-2` and its offset). 2. Search the host stylesheet `/one/assets/index-*.css` for `focus-visible\:ring-ring`: present, since the kit uses it.
**Applies to:** any BlueStep One component

### P-53 — To check a page at 1440 × 900 when the window cannot be resized, load it in a same-origin iframe of that size

Legacy shape: a Manage page is checked in whatever window is open. BlueStep One shape: the design audit's numbers are at 1440 × 900 (the canvas's window), and the host's widths follow the window (`main` is the window less the 240 px column; the page column is at most 1280). So, in a tab of its own on the same origin: `document.body.innerHTML = ''`, then an `<iframe id="w1440">` with `src = location.href`, `position: fixed; top: 0; left: 0; width: 1440px; height: 900px; border: 0`. Inside it `innerWidth` is 1440 and `main` 1200, as on the canvas. Work through `const w = document.getElementById('w1440').contentWindow`: `w.eval(<source>)` runs `${CLAUDE_PLUGIN_ROOT}/tools/computed-styles.js` and `${CLAUDE_PLUGIN_ROOT}/tools/fetch-wrapper.js` inside the frame (if the page's policy allows it), and the frame's `w.performance` shows which build it loaded. Two catches: a new tab starts on the site's first unit (the unit is kept per tab), so pick the unit in the frame's switcher and then `w.location.reload()` (a hash change alone can leave a skeleton titled "Page"); and a screenshot of a tab in the background times out, so read with a script tool and click with `el.click()` or dispatched pointer events rather than by coordinates; in such a tab transitions do not run either, so turn them off while measuring.
When not to use: when the window itself can be set to 1440 × 900; then check it there, as a person would see it.
**How to tell.** 1. On a test org, in a tab of its own, clear `document.body` and add an `<iframe>` of the same page, `position: fixed`, 1440 × 900. 2. Inside it, `innerWidth` is 1440 and `main` 1200, as on the canvas; run `computed-styles.js` through the frame's `eval`.
**Applies to:** any BlueStep One component

### P-54 — A component's reads get a deadline in two places: its own `/gql` helper and a host wrapper made once per mount

Legacy shape: a Manage page is one server render; a dropped request shows as a browser error page, and F5 is the cure. BlueStep One shape: a component's screen waits on several reads, some shared across mounts, and the host sets no deadline on reads (G-235). So: `withDeadline(promise, ms, signal?, cancel?)` rejects with the `network` error the screens already word once the time runs out (20 s), lets the caller's abort win, and calls `cancel` so the request itself is aborted, not only forgotten. The `/gql` helper runs the token's `HEAD` and every query through it, from the POST to the end of the body, and leaves mutations alone (a write may still land after any deadline; its path words a lost answer itself). And `readDeadlineHost(host)`, a `Proxy` made once in the factory, races only the host's read methods (a list typed against the host's declarations, so a misspelt name fails the type check), binds every other member to the real host, and is what the screens receive, so effects keyed on `host` stay stable. A shared promise that times out is dropped like a failed one, so the next screen asks again.
When not to use: writes; and a read whose answer can legitimately take longer than the deadline (a large export), which needs its own, longer one.
A copy of these helpers in another component covers only the reads its source makes: add the copy's own host reads to the list of host reads, and put any direct `fetch` under `withDeadline` (G-245).
**How to tell.** 1. In a component with these helpers, run the tests of `withDeadline`: it rejects with `network` after 20 s and aborts the request. 2. On a test org, hold the screen's main read in the page past 20 s (`fw.delay`, P-35): the screen shows its error with *Try again*.
**Applies to:** any BlueStep One component

### P-59 — BlueStep One: a module-level session cache exports a reset that the tests call in `afterEach`

BlueStep One shape: a value read once a session (a form's model, a token, the server's clock offset, a form's labels) lives in a module-level `Map` or variable, and the module exports a one-line reset beside it (`forgetX()` or `clearX()`). Each test file calls every reset its module holds in `afterEach`, so a test that fills the cache never answers for the next one, and a test can count reads exactly (one read, then none from the cache, then one again after a failure). A failed read is taken out of the cache at once, so the next caller tries again; a read in flight is the cached promise, so two callers at the same time share one read. Without the reset, a test that passes alone fails or passes by luck in the full run, depending on which tests ran before it.
**How to tell.** 1. In a component with a module-level cache, find the exported resets and the test files' `afterEach` that calls them. 2. Remove one reset from `afterEach` and run the full `node --test`: a test that shares the cache (two reads at the same time sharing one) fails, though it passes alone.
**Applies to:** any BlueStep One component

### P-61 — BlueStep One: one write engine per component, each row type a "subject" (its form, field specs, read and words), not a copy per type

Legacy shape: Manage has one entry page per form, each with its own save. A first BlueStep One shape put the whole write path (changed fields only, signature last, request id, resend once with the same id, re-read, conflict judge, the words) in one save function for one form alone, so a second row type would mean a second copy of all of it. BlueStep One shape: the engine takes a *subject* (`form`, the field specs that map edits to `fieldValues` and back, the signature fields, `read`, `idOf`, `versionOf`, `signatureOf`, the saved-by-someone-else and removed messages), and each row type is a few dozen lines of specs. A parent entry and its child entry share one engine on one screen; a third form is another subject. The tests send each probe write through the engine and `deepEqual` the request against the probe's recorded request, so a subject's spec is checked against the server's own answer. When not to use it: a write with no signature and no conflict to judge (a settings save) needs none of it.
**How to tell.** 1. In a component that saves more than one form, read its write module: each save calls one engine with a subject (form, field specs, signature fields, `read`, the messages). 2. Run `node --test`: the write tests `deepEqual` each request against the recorded probe answers.
**Applies to:** any BlueStep One component

### P-62 — BlueStep One: a row changed by someone else (or removed) during a save keeps its place on the page, placed by the version sent and drawn at its newest

Legacy shape: a Manage page reloads after a save, so an entry another user signed meanwhile simply moves to its *Done* section, and the user's typed values are gone without a word. BlueStep One shape: the page keeps a map of the rows whose save came back "saved by someone else" or "removed". Each is placed in its section by the version that was sent (so it stays where the user was looking), drawn at the newest version read back (the other signer's values, or locked when removed), with its sentence, until the page is left. The sectioning function stays pure and unchanged. When the other signer is the viewer themself (the same user in another tab or in Manage), read the conflict as saved and let the row move to *Done*.
The same holds for a row whose second write failed: a parent entry that landed while its child entry was refused ("The entry was saved, but its child entry was not.") first folded into *Done*, hiding the open child while the footer still asked to save. Kept in place, it stays signed with its sentence and the child under it until the child goes alone (P-63).
Seen live: the save answered `CONCURRENT_MODIFICATION` with `currentVersion`; the card kept its place, drawn done with "Done at <time> by <signer>" and the sentence "<signer> signed this entry at <time>. Your changes to it were not saved."; the footer read "No unsaved changes".
When not to use: a list sorted by a value the other user changed, where staying put would mislead.
**How to tell.** On a test org, open a test entry with a Signature field in a component screen, edit it without saving, have a second user sign the same entry in Manage meanwhile, then *Save*: the entry stays where it was, drawn at the other signer's version with its sentence.
**Applies to:** any BlueStep One component

### P-63 — BlueStep One: resending the second half of a two-form save alone copies in what the first half sent

Legacy shape: a Manage page saves a parent entry and its child entry in one post, so the child always gets what the parent shares (a note, a typed time, shared values). BlueStep One shape: the parent goes first, then the child; the write copies the shared values into the child only when it sends both. When the child fails after the parent landed, the page keeps the parent part that went, and *Save* sends the child alone with that part copied in by the same function, falling back to the parent as stored. Checked live: the child resent alone saved the shared values, and the parent kept its relationship field to it.
**How to tell.** 1. On a test org, save a test parent entry that also writes a child entry, and make the child's write fail in the page (`fw.refuse("<child mutation>")`, P-35): the parent lands, the child is kept. 2. Clear the rule and *Save* again: the child goes alone and carries the parent's shared values.
**Applies to:** any BlueStep One component

### P-65 — BlueStep One: test a React hook under `node --test` with a stand-in for `react` and Node's mock timers

BlueStep One shape: a component repo has no `react` installed (the host serves it) and Node runs no `.tsx`, so a hook in a `.ts` file (a poll, a timer) is tested by running it on a small stand-in for the hooks it calls (`useState`, `useRef`, `useEffect`: render again when a state changes, run an effect when its deps changed, its cleanup before the next run and on unmount), mapped in for `react` by the tests' resolve hook (a loader module that serves the stand-in as a `data:` URL). `mock.timers.enable({ apis: ["setTimeout", "Date"] })` drives the clock. A poll that sets its next timer only after the read's promise settles needs a long wait stepped in pieces of the poll's interval, each followed by a `setImmediate` flush, since one `tick` fires one timer. Check the tests catch a fault by breaking the hook on purpose (the callback on the wrong condition, no `clearTimeout`): each break should fail at least one test. The stand-in holds only the part of React's contract the hook uses; anything about rendering (a provider, where a note is drawn) stays a source-text check or the live check.
**How to tell.** 1. In a component with a poll hook, run `node --test` on its test: the hook runs on the stand-in for `react` that the resolve hook maps in, with `mock.timers`. 2. Break the hook on purpose (drop its `clearTimeout`): tests fail.
**Applies to:** any BlueStep One component

### P-67 — An editor the page opened by itself is not unsaved work until the user changes a value in it

Legacy shape: a Manage page opens with no sub-editor open; the user opens one. BlueStep One shape: a screen made from a pre-fill (a new entry made from another entry) opens its first child editor by itself, filled from the source, and the page's unsaved guard would count any open editor as unsaved work, so leaving untouched would ask about nothing the user did. Keep a flag `autoOpened` while the page's own editor is open, leave it out of the unsaved check, and clear it on the user's first value change (an `onTouched` the editor calls from its change helper and from every free-text `onChange`, never on blur or focus) and when the user opens an editor themselves (with *Add* or *Change*). Seen live: before the fix, a value typed into the auto-opened editor left the footer at "No unsaved changes", so leaving lost it with no guard; after it, the first change makes the footer unsaved. Test it as text: the editor calls `onTouched?.()` from every change path. When not to use: an editor the user opened is unsaved work from the start.
**Applies to:** any BlueStep One component

### P-68 — Send a field a create needs only when the form has it, and leave the feature out when it does not

Legacy shape: Manage's page shows only the fields the form has. BlueStep One shape: a component builds its create's `fieldValues` in code, so a field added for a new feature (a relationship field that links the new entry to its source) is sent on every org the component runs on. On a form that lacks it, every save on that path is refused (`PRECONDITION`, "Unknown or non-editable field.") and the viewer sees the server's developer message. Look the field up first in the form's fields read (by its formula id) and turn the feature off when it is missing: no banner, no pre-fill, no link, a plain new entry. When not to use: a field the screen cannot work without; then say so on load, before the user types anything.
**Applies to:** any BlueStep One component

### P-69 — A write that lands after the host navigated away neither draws nor navigates

Legacy shape: a Manage page posts and the server answers with the next page, so a save cannot land on a page already left. BlueStep One shape: a save is a `/gql` promise, and the viewer can leave through the host's own navigation (the nav, a breadcrumb) while it runs; when it lands, a handler that sets state or calls the host's navigation pulls the viewer back to the list, or writes a tab choice for a page they left. Keep `const alive = useRef(true)`, set it false in an effect's cleanup, and return early from every handler a write resolves into when it is false. When not to use: work that must finish whether or not the screen is there (the write itself; only its drawing and navigation stop).
**Applies to:** any BlueStep One component

### P-70 — Hold a button that waits for an answer with `aria-disabled`, not `disabled`, and say why beside it

Legacy shape: a Manage page refuses the save and shows the message after the click. BlueStep One shape: the button is held until the question is answered (a confirm button held until a required question in the dialog is answered; a *Try again* held while its read runs), with `aria-disabled="true"` and a click handler that does nothing, not the `disabled` attribute: a `disabled` button leaves the Tab sequence, drops focus if it had it, and a screen reader never reaches the reason written under it. Tie the reason to the button (`aria-describedby`). When not to use: while a write runs, every button is plainly `disabled` (nothing to explain), and focus moves to the next action when the step changes (G-318).
**Applies to:** any BlueStep One component

### P-71 — Keep a failed read's warning drawn while *Try again* runs, and let the button say it is running

Legacy shape: Manage reloads the page, and the browser shows it is loading. BlueStep One shape: a read in an effect keyed on an `attempt` counter. *Try again* sets a `retrying` flag and bumps `attempt`; the effect does not reset the state to "loading" at its start, so the warning stays where it was, and it clears `retrying` when its read settles either way (an aborted run is followed by one that settles). The button shows a spinner and "Trying again…" while `retrying` is true, held with `aria-disabled` (P-70); the changed words inside the warning's `role="status"` are what a screen reader hears. A read again that nobody clicked (after a save) bumps `attempt` only, so no button says "Trying again…". Say a failure where the missing data is used (the card that needs it) rather than over the page, and say what still works. When not to use: a first read, which has nothing to keep drawn; there the loading state is right.
**Applies to:** any BlueStep One component

### P-72 — Say where focus goes next in a ref, and move it once in an effect after the render that draws it

Legacy shape: a Manage page reloads after a save, and the browser puts focus at the top. BlueStep One shape: a control that swaps one view for another (a card's edit view for its read view) loses the focused button in the swap. Set `focusNext.current = "edit" | "save"` where the change is decided (the *Cancel*, the save's outcome), and in an effect that runs after every render read it, clear it, and focus the target only if the state that draws it holds (`state === "signed"` for *Edit*). The focus moves once, after the target exists, and a later render does not steal it back. Seen live as a staff user and as an admin. When not to use: a dialog's own close (G-320 has its hook).
**Applies to:** any BlueStep One component

### P-73 — A field the page holds is never checked on save

Legacy shape: Manage's required marks apply to fields the user can still change. BlueStep One shape: a screen that holds fields after a signature (as Manage's edit page does for a signed record) must not refuse a save over one of them, since the user cannot fix it: an entry Manage saved with a required relationship left empty, or a legacy entry with no value in a field that is required now, would refuse every later edit of its child rows. Pass the locks into the checks and skip what they hold; keep checking what stays open. When not to use: a field the server refuses empty; then say so and point to where it can be fixed.
**Applies to:** any BlueStep One component

### P-76 — Read the viewer's rights from `/gql` before drawing actions, write through one helper that returns the server's warnings, and show a reasoned refusal in the server's words

Legacy shape: Manage draws a form read only, or leaves out *Add*, from the viewer's groups, and shows a formula's `sendMessage` text on the page it returns to after the save. Before release 26.10.26 BlueStep One had neither: a component drew every action and learned rights from the first refusal (P-14), and a formula's messages never came back, so screens copied the formulas' checks or messages.
BlueStep One shape (from release 26.10.26.01 on):
1. **Rights up front, with the rows the screen already loads:** `canEdit canDelete` on each `FormRow` (also served in `formEntries … formEntry` and `remoteObjects … on FormRow`), `canEdit` on each cell the screen edits, and `RelateForm.createLevels(record) { canCreate creatableFields }` for *Add* / *New*. Fold them with a pure `rightsFromServer(canAct)` into the screen's existing rights mode (basis `server`), so the read-only drawing is the same one a refusal used.
2. **Decide from the field that matters, not the row alone.** A row reads `canEdit: true` when the viewer may write any one field, and `canCreate: true` when they may create any one field. A reader with field-level Editor on a few fields reads both true. So an entry is editable when the row and its key field's cell (the entry's name, say) both read `canEdit`; *Add* needs `canCreate` and the key field in `creatableFields` (by topId); each input follows its own cell.
3. **Writes through `gqlWrite(query, variables, signal)`**, which returns `{ data, warnings }`: the response's `extensions.warnings`, each as `{ text, links }` (tags dropped, entities decoded, white space folded, the `<a href>`s kept). Show them where the saved result already shows (a *Saved* notice, the card), never in a new dialog or banner; a link opens the BlueStep One page for its target if there is one, else Manage (custom links and pages still open Manage). `gql()` keeps returning `data`, so readers do not change. A warning keeps its links' addresses, not which words were linked, so a message with a link is drawn whole as one link to its first address. A write whose screen goes away when it lands (a create that opens the new entry, a delete that goes back to the list) hands its warnings to the next screen, which takes them once when its load lands.
4. **Refusals:** the kind from `extensions.code`, falling back to `classification`; `extensions.reason` (`FORMULA_REFUSED`, `VALUE_REFUSED`) kept on the error. A refusal with a reason shows the server's words after the not-saved line, is never hidden by a generic line, and is not read as "the row moved". A write that answers an error saved nothing (fixed in 26.10.26), so no read-back "saved anyway" recovery.
5. **The refusal stays the fallback:** a failed rights read leaves the screen as before (optimistic), and a FORBIDDEN on save still turns it read only, for a right that changes while the screen is open. Signed out comes only from `UNAUTHENTICATED`; no probe after a FORBIDDEN.
Seen live on 26.10.26.01: a create's two formula messages showed in the *Saved* notice, one as a link to Manage; a staff reader's list showed no *Add* and no actions; the reader's entry drew read only on load, with no refusal first.
When not to use: on an org before 26.10.26 the fields are not served; keep P-14 there. A filled signature reads `canEdit: true` for staff though clearing it over `updateFormRow` is refused for anyone but an admin: keep the screen's own lock for that. A Super viewer sees no change, so check with a staff editor and a staff reader whose rows really read `canEdit: false` (a user who writes to the form reads true there), beside Manage on the same entry.
**Applies to:** any BlueStep One component
