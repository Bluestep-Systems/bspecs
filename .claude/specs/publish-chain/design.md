# Design — Publish chain (b6p-cli → bspecs)

**Status:** Drafting

This is primarily a **release / packaging** change, not a feature in `src/`. No scaffolder logic
(`cli.js`, `src/scaffold.js`, the template engine) changes. The work is: publish an upstream
package, rename + rewire this package's metadata, move the repo to the org, and publish.

## Files / areas affected

### This repo (`bspecs`)

- `package.json` — three edits: `name` → `@bluestep-systems/bspecs`; add
  `dependencies["@bluestep-systems/b6p-cli"] = "^0.1.0"`; fix
  `repository.url` → `https://github.com/Bluestep-Systems/bspecs.git`. Bump `version` 0.7.0 → 0.8.0
  at the publish step.
- `package-lock.json` — regenerated by `npm install` after the `package.json` edits (new dep + name).
  Not hand-edited.
- `.npmrc` (**new**, repo root) — scope mapping `@bluestep-systems:registry=https://npm.pkg.github.com`
  plus `//npm.pkg.github.com/:_authToken=${GITHUB_TOKEN}`. Token is an env placeholder; **no secret
  committed**. Because the package is published under `@bluestep-systems`, a single scope mapping
  covers both bspecs itself and its `b6p-cli` dependency (the rename removes the need for a second
  `@bluestep` mapping).
- `README.md` — update the title and the two `npm install -g @bluestep/bspecs` /
  `npm update -g @bluestep/bspecs` lines to the new name; add a **consumer auth** section (`.npmrc` +
  `read:packages` PAT) so a clean-machine install resolves both packages.
- `CLAUDE.md` — update the intro line and the "Publishing" section (new package name, the new
  `b6p-cli` dependency, org repo URL).
- `CHANGELOG.md` — new `## [0.8.0]` entry (rename, new dependency, org move). The top "All notable
  changes to `@bluestep/bspecs`" line updates to the new name. **Historical entries that mention
  `@bluestep/init` or the older `@bluestep/bspecs` rename are left untouched** — they are an accurate
  record of past releases.
- `TODO.md` / `DONE.md` — check off the items this resolves ("Push to GitHub", "Consumer auth docs",
  upstream-publish item); archive to `DONE.md` per the repo convention.
- Git remote — `origin` repointed from `git@github.com:fchazarreta-bs/bspecs.git` to the org repo
  (config-only, not a file edit).

### Upstream monorepo (`Bluestep-Systems/vscode-extension`, WSL `/home/fchazarreta/vscode-extension`)

## Approach

Sequenced because steps depend on each other:

1. **A0 — auth (gate).** Confirm org membership + publish rights and a `~/.npmrc` with a
   `write:packages` PAT. Nothing else can succeed without this. No repo changes; a verification step.
2. **A2 — publish `b6p-cli`.** Operational, in the monorepo. `b6p-cli` must exist on GitHub Packages
   *before* bspecs can declare it (or `npm install` in A3 fails to resolve). Verify with
   `npm view … version` and a clean global install of just the cli.
3. **A3 — rewire bspecs.** Edit `package.json` (name, dep, repository), add `.npmrc`, run
   `npm install` to refresh the lockfile, update README/CLAUDE.md, create the org repo, repoint
   `origin`, push `main`.
4. **A4 — publish bspecs.** Bump to 0.8.0 + CHANGELOG, `npm publish`, verify a clean global install
   pulls `b6p-cli` transitively and `b6p --version` resolves.

The rename to `@bluestep-systems/bspecs` is treated as a coherent unit with the dependency add and
`repository` fix — all three are `package.json` edits that only make sense together and share the
lockfile refresh.

## Data / control flow

End-to-end consumer flow this enables:

```
npm i -g @bluestep-systems/bspecs
   └─ npm reads ~/.npmrc  →  @bluestep-systems  →  npm.pkg.github.com (PAT: read:packages)
        ├─ fetches @bluestep-systems/bspecs@0.8.0
        └─ resolves dep @bluestep-systems/b6p-cli@^0.1.0  →  same registry
              └─ installs b6p bin  →  on PATH  →  `b6p --version` works
```

No scaffold template trees or `{{VAR}}` substitution are involved — `copyTemplateTree` and
`applyTemplate` are unchanged. This is a packaging/distribution change layered on top of the
existing scaffolder.

## Edge cases

- **Ordering:** if A3's `npm install` runs before A2 publishes, dependency resolution 404s. A2 must
  complete (verified via `npm view`) first.
- **`@bluestep` → `@bluestep-systems` rename leftovers:** historical CHANGELOG lines mentioning the
  old name must NOT be rewritten. Only living references (README, CLAUDE.md, TODO.md, the new
  CHANGELOG entry, the CHANGELOG top line) change. Confirmed scope: 5 living-doc files; **no
  `templates/**` references**, so scaffolded output is unaffected.
- **Lockfile:** after the name + dep edits, `package-lock.json` must be regenerated (`npm install`)
  so the published tarball's lockfile is internally consistent; don't hand-edit it.
- **Secret hygiene:** `.npmrc` uses `${GITHUB_TOKEN}`; the literal PAT lives only in the env / the
  user's `~/.npmrc`, never in the committed file. Confirm `.gitignore` doesn't need a tightening and
  that the committed `.npmrc` has only the placeholder.
- **WSL-vs-Windows PATH (observe, don't fix here):** A4 verification records whether the
  globally-installed `b6p` is reachable from the WSL hooks/skills. The fix (switch to `npx b6p`) is
  the A5 spec; this spec only captures the observation.
- **Repo move:** moving `origin` to the org must not orphan open work — branch `feat/b6p-subagents`
  and any tags should push cleanly to the new remote.

## Alignment with existing patterns

- **Publishing conventions** (CLAUDE.md "Publishing"): GitHub Packages, `access: restricted`,
  `files` allowlist (`cli.js`, `src/`, `templates/`). This spec keeps all of that and only changes
  the scope and adds a runtime dependency.
- **Docs-in-sync rule** (CLAUDE.md "Working on tasks"): CHANGELOG/README/CLAUDE.md/TODO.md updated
  alongside the change.
- **ADR coverage:** the end state is already designed in
  [b6p-cli-distribution.md](../../../docs/decisions/b6p-cli-distribution.md). This spec executes its
  "publish, then declare the dependency" path. **One ADR update is warranted:** the ADR currently
  assumes an *upstream issue / peer-dependency* route (Options A + E). We are instead publishing
  `b6p-cli` directly and using a plain `dependencies` entry now. A short note (or status bump) on
  the ADR recording "published directly; `dependencies` not `peerDependencies` for the first
  release; peer-dep + `npx` deferred to the A5 spec" keeps the record honest. The package **rename**
  decision (`@bluestep` → `@bluestep-systems`) is also ADR-worthy as a one-liner, since it was a
  flagged human call — fold it into the same ADR note.
- **English-only docs** (memory / project rule): all new prose in English.

## Risks

No test suite, so verification is manual and registry-observable:

- **Resolution failure after publish** — mitigated by verifying `npm view @bluestep-systems/b6p-cli
  version` returns `0.1.0` before A3, and a clean-dir `npm i -g @bluestep-systems/bspecs` in A4.
- **Wrong tarball contents for b6p-cli** — mitigated by `npm pack --dry-run` (expect exactly
  `dist/cli.js`, `package.json`, `README.md`, `CHANGELOG.md`).
- **Publishing the wrong bspecs files** — the existing `files` allowlist already constrains this;
  re-verify with `npm pack --dry-run` before A4.
- **Irreversible-ish actions** (publish to a registry, create/rename the org repo): publishing a
  version cannot be re-published under the same number — get A0 + dry-runs green first; treat the org
  repo creation as a one-way door and confirm the exact name in A0.
- **Auth confusion** — the consumer needs `read:packages`; the publisher needs `write:packages`.
  Documented separately in README so a consumer doesn't fail with a publisher's assumptions.
